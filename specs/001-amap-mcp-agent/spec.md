# Feature Specification: 可解释的地图对话 Agent

**Feature Branch**: `001-amap-mcp-agent`  
**Created**: 2026-09-26  
**Status**: Draft  
**Input**: 用户希望构建一个小型 Agent，通过高德地图 MCP 服务完成大模型自身无法可靠完成的外部地图查询，并在对话中展示 MCP 的使用过程。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 对话式地点搜索与过程观察 (Priority: P1)

学习者用自然语言描述要找的地点，例如“帮我找北京大学东门附近的咖啡店”。Agent 识别这是需要外部地图数据的问题，查询地图服务，并以对话形式给出匹配地点；同时让学习者查看从工具选择到最终回答的完整过程。

**Why this priority**: 这是最短、最清晰的 Agent 使用 MCP 的闭环：语言理解不能替代实时地点数据，工具调用结果直接决定回答。

**Independent Test**: 输入一个明确的地点搜索请求，确认系统给出至少一个来自地图服务的候选地点，并展示工具选择、输入摘要、结果摘要和最终答复四个阶段。

**Acceptance Scenarios**:

1. **Given** 用户提交包含地点或附近设施的明确搜索请求，**When** Agent 可获得地图服务，**Then** 系统返回与请求匹配的地点结果，并标明结果来自外部地图查询。
2. **Given** 用户提交地点搜索请求，**When** Agent 完成外部查询，**Then** 用户可查看本次会话的工具选择、已脱敏的输入摘要、结构化结果摘要和最终回答。
3. **Given** 搜索结果存在多个合理候选地点，**When** 用户的描述不足以唯一确定地点，**Then** 系统呈现候选项或请求用户补充信息，不得把任一候选项伪装成唯一答案。

---

### User Story 2 - 基于实时地图数据的路线建议 (Priority: P2)

用户用自然语言给出起点、终点和可选的出行偏好，例如“从晋中学院到太原南站，推荐公共交通路线”。Agent 查询地图服务并给出可执行的路线建议，而不是依靠模型记忆臆测路线。

**Why this priority**: 路线会受地点解析、交通方式和实时地图数据影响，能直观体现工具将 Agent 的能力扩展到模型知识之外。

**Independent Test**: 对两个可解析地点提交路线请求，确认最终答复包含起点、终点、出行方式和地图服务返回的路线关键信息，并能查看相应调用过程。

**Acceptance Scenarios**:

1. **Given** 用户提供可解析的起点和终点，**When** 用户请求路线，**Then** 系统返回符合所选或默认出行方式的路线建议及关键行程信息。
2. **Given** 用户未提供完整的起点、终点或出行方式，**When** 信息不足以获得有意义的路线，**Then** 系统用简短问题补齐最关键的信息后再查询。
3. **Given** 地图服务无法为该请求返回路线，**When** Agent 收到失败或空结果，**Then** 系统清楚说明限制并给出下一步建议，不得编造路线细节。

---

### User Story 3 - 外部信息与失败边界演示 (Priority: P3)

学习者提出地图服务支持的其他动态信息问题，例如某地周边设施或出行相关状态，并通过结果与过程记录区分“模型推理”和“外部事实”。当服务不可用或调用失败时，学习者也能理解失败发生在何处。

**Why this priority**: 这使项目从“能调工具”提升为“能解释工具价值与边界”的学习演示，但不阻塞地点搜索和路线规划这一最小可用版本。

**Independent Test**: 对一项已由地图服务声明支持的动态信息能力发起查询，并模拟一次服务失败；确认前者使用外部结果回答，后者保留清晰的失败阶段和用户可采取的动作。

**Acceptance Scenarios**:

1. **Given** 地图服务声明支持某项动态地图信息，**When** 用户提出对应问题，**Then** 系统查询该服务并在回答中区分外部查询结果与 Agent 的解释。
2. **Given** 地图服务不可达、拒绝请求或返回无效结果，**When** 调用结束，**Then** 系统记录失败阶段与面向用户的说明，且不泄露凭据或敏感配置。

### Edge Cases

- 用户只说“带我去机场”但未提供当前位置或目标城市时，系统应请求最少的补充信息。
- 用户输入的地名有多个同名结果时，系统应展示候选项或说明采用的匹配条件。
- 地图服务返回空结果、超时或不可用时，系统应明确区分“未找到”和“暂时无法查询”。
- 用户请求的能力不在已连接地图服务提供的能力范围内时，系统应说明当前不支持，并且不得伪造外部结果。
- 过程展示中不得显示访问凭据、完整密钥或其他敏感配置。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户通过自然语言发起地点搜索、周边地点搜索和路线规划请求。
- **FR-002**: 系统 MUST 在需要外部地图事实时调用已连接的高德地图 MCP 服务，而不是仅依据模型记忆生成地点、路线或动态信息。
- **FR-003**: 系统 MUST 将地图服务返回的结构化信息转换为简洁、可读且与用户问题相关的对话回答。
- **FR-004**: 系统 MUST 为每次外部地图查询保留并展示以下可理解的过程信息：Agent 的工具选择、已脱敏的输入摘要、结构化返回摘要、最终回答。
- **FR-005**: 系统 MUST 在地点或路线信息不足、歧义或无结果时，请求补充信息或呈现候选项；不得把推测结果表述为已验证的地图事实。
- **FR-006**: 系统 MUST 使用户能指定路线的起点、终点和出行偏好；缺失时使用明确说明的默认值或追问。
- **FR-007**: 系统 MUST 仅对地图服务实际声明支持的动态信息能力发起调用，并在回答中说明该信息来自外部查询。
- **FR-008**: 系统 MUST 在服务不可用、调用失败或结果格式异常时提供可理解的错误说明、记录失败发生的阶段，并且不得捏造查询结果。
- **FR-009**: 系统 MUST 在全部过程展示和错误信息中隐藏访问凭据及其他敏感配置。
- **FR-010**: 第一版 MUST 不包含账户体系、跨会话历史保存、地图可视化、收藏功能、多智能体协作或非地图类服务集成。

### Key Entities

- **对话请求**: 用户的自然语言问题，以及已确认的地点、路线和出行偏好。
- **地图查询**: 为回答某个对话请求而发起的一次外部地图信息查询，包含目的、输入摘要和结果状态。
- **地点候选项**: 地图服务匹配到的一个地点，包含用于用户判断的名称、位置和相关描述。
- **路线建议**: 起点、终点、出行方式及地图服务提供的行程关键信息。
- **调用过程记录**: 对话请求到最终回答之间的可解释链路，包含工具选择、脱敏输入摘要、结果摘要和失败信息（如有）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对 3 个预先定义的地点或周边地点搜索请求，用户均能在一次对话中获得至少一个由外部地图查询支持的结果，并查看完整调用过程。
- **SC-002**: 对 3 个预先定义、起终点明确的路线请求，用户均能获得包含起点、终点、出行方式和至少一项行程关键信息的路线建议，或获得明确的查询失败说明。
- **SC-003**: 在所有成功或失败的外部查询演示中，用户均能区分工具选择、输入摘要、结果摘要和最终回答四个阶段，且过程信息不包含访问凭据。
- **SC-004**: 对地点歧义、信息缺失、空结果和服务不可用四类场景，系统每类均给出明确下一步或限制说明，不输出未经外部验证的地图事实。
- **SC-005**: 初次使用者可在 10 分钟内完成一次地点搜索和一次路线查询，并能口头说明 Agent 何时使用了外部 MCP 工具。

## Assumptions

- 项目的主要使用者是希望理解 Agent 与 MCP 协作方式的学习者，而非生产环境的终端用户。
- 使用者会在运行前获得可访问的高德地图 MCP 服务及其所需的合法配置；凭据由运行环境提供，不进入对话或过程记录。
- 第一版以中文对话为主，默认服务范围和实际可用能力以连接的地图服务声明为准。
- 外部地图信息可能变化，因此系统只将成功调用返回的信息视为当前可用事实。
- 第一版聚焦命令行或简单对话界面的学习演示，不要求嵌入式交互地图或长期数据保存。
